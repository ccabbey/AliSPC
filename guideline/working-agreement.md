# 协作约定（用户明确要求，优先级最高）

这些是用户在多轮沟通中下达的 standing constraints，接手后必须原样遵守。引用为用户原话。

## 1. 落盘权限：默认只给代码，不动文件

> "从现在开始不要编辑已落盘文件了，除非我明确指示你这么做。给出修复方案即可。"

> "不用落盘文件，直接输出代码我自己更新，然后我重新到处平铺文件"

- 默认交付方式：**聊天里输出代码块 / 修复方案**。用户在 VBE 里应用，然后重新导出平铺文件到 `src/`。
- 只有用户明确指示（如"落盘"、"开干吧，落盘文件"）才写磁盘。新建文档（如本 guideline）同样需要明确指示。
- 评估类请求（"你再评估下"）只输出分析，不顺手改文件。

## 2. 源文件基准与 GBK 机制

- `src/` 平铺文件是**唯一代码基准**。不要解析 xlsm、不要从工作簿反推代码。
- 编码必须保持 **GBK(GB2312) + CRLF**。Read 工具读 GBK 会显示中文乱码，但 ASCII 代码可用；Edit/Write 工具会拒绝非 UTF-8 文件。
- **已接受的落盘机制**：python 脚本（脚本本身 UTF-8），`io.open(path, encoding="gbk", newline="")` 读写；替换前断言锚点出现次数；写后断言 CRLF 纯净 + 回读关键标记。脚本放系统 Temp（本机产物，不随项目迁移）。
- 读 GBK 的 `todo.md` 用 python 解码，同属已接受实践。
- **改前重读**：用户会并发改代码。历史实例：用户自行把 `SeriesDump.Write` 改名 `WriteData`、临时屏蔽 `ToMsoAnchor`、应用 `FormatNumber` 合并、改 demo 数据范围。任何"上次读到的内容"都可能过期。
- **未保存的工作簿是旧快照**：判断改动成败以平铺文件为准，先核对再下结论。

## 3. 验证与 token 节约

> "关于后续的测试流程，我们再对齐一下，因为你调用工具链会消耗很多token，而我希望尽可能节省token，所以我希望你能尽可能的不要动用python，powershell等等工具链来验证或测试你的想法，也不要采用后台开一个excel进程或是com注入等等方法。如果你有要验证的猜想，先整理成待办项告诉我，得到我的明确同意后再调用你的工具链。"

边界：

| 无需审批 | 需要用户明确同意 |
|---|---|
| Read / Grep / Glob 静态检查 | 运行任何测试 / 探针脚本 |
| python 作为 GBK 编辑机制（含回读断言） | PowerShell、COM 自动化、后台 Excel 进程 |
| 解码 GBK 的 todo.md | 安装依赖、其他消耗 token 的工具链验证 |
| 任务管理 | |

- 流程：**猜想 → 整理成待办 → 用户明确同意 → 才执行**。
- 验证以用户侧为主：VBE 编译、运行 demo、观察渲染、MsgBox/Debug 输出。
- 历史例外：2026-11-10 的轴拓扑 COM 探针经过批准，结论已固化在 `excel-rendering-notes.md`（探针脚本在旧机器 Temp，不随项目迁移；结论可复用，不必重探）。
- Trust Center 会阻止程序化访问 VBProject，不要尝试代码注入。

## 4. 分工边界

- **用户负责**：VBE 导入/导出平铺文件、Rubberduck 维护（`VB_PredeclaredId` 等属性）、工作簿侧一切、编译与渲染验证、并发改代码。
- **agent 负责**：方案评估、代码生成、指示后的落盘（python 机制）、静态一致性检查（如 grep 调用点、跨模块成员解析）。
- 不要试图修复工作簿；不要改 `Attribute VB_*` 行。

## 5. 沟通与决策风格

- 中文沟通；先评估（可行性 / 取舍 / 影响面 / 风险），等用户拍板，再实现。
- **不要过度设计**（用户反复强调）：不为假设需求加配置项、预留扩展点、拆分无功能差异的函数。
- 已锁定的决策不重开（清单见 status-and-tasks.md）。
- 用户推翻推荐时（如密度纵轴圆整到 Decimals），按用户决定执行，不再争论。
- 诚实汇报：改了什么、验证了什么、什么没验证；不声称做过的验证之外的事。
- 用户技术能力强，会自行核对分支与渲染结果；给结论时附原因和可核对的点，不堆砌过程。
